## 高严重度

### H1. 数据库 N+1 查询：`buildPathFromMusicRecord` 重复查 `music_dir`
- **状态**：已修复
- **修复说明**：`buildPathFromMusicRecord` 增加可选 `dir_path` 参数，调用方已 JOIN 出该字段时直接使用，跳过查库；`db.ts` 内约 17 处调用点已改为传入 `row.dir_path`；`getMusicWithoutLyrics`/`getMusicWithClaimedLyricsPath`/`getMusicWithoutCover`/`getMusicWithClaimedCoverPath` 4 条原本没有 JOIN 的 SQL 补了 `JOIN music_dir` + `dir_path` 选择。`cleanupMissingLocalMusic`（约845行）未在本次范围内，其查询未选 `dir_path`，保持原查库回退逻辑不变。
- **位置**：[pathUtils.ts:250-264](../../src/main/database/pathUtils.ts#L250-L264)，调用点分布在 [db.ts](../../src/main/database/db.ts) 约19处（`mapSearchResultRows`、`getAllMusicById`、`getAllMusicByPath`、`getMusicWithoutLyrics`/`getMusicWithoutCover`、`advancedSearch`、`getMusicByHash`、`getMusicByGenre`、`getLocalMusicByMusicId`、`getFavoritesByMusicId`、`getPlaylistSongsByMusicId`、`getRecentPlaysByMusicId`、`getPlayQueueByMusicId`、`getDiscoverMusicByMusicId`、`getLocalMusicPaginated` 等）
- **问题**：查询已 JOIN 出 `dir_path`，但拿到结果后又调用 `buildPathFromMusicRecord` 对每一行重新 `SELECT path FROM music_dir`。`pathUtils.ts` 里已经写好的 `MusicDirCache`（270-366行）完全没被引用，是"建好了但没接上"的死代码。
- **影响**：几乎所有分页/搜索接口都会产生 N+1 查询，量大后明显拖慢响应。

### H2. 搜索全表扫描：LIKE 两端通配导致索引失效
- **状态**：已修复
- **修复说明**：`searchMusicPinyin` 的 LIKE 参数由两端通配 `%q%` 改为前缀通配 `q%`，使 `idx_all_music_search_pinyin`/`idx_all_music_search_initials` 索引生效。代价：拼音/声母搜索不再匹配中间片段，仅匹配开头（用户已确认接受该取舍）。`searchMusicLike`/`getSearchSuggestions` 未改动。
- **位置**：[db.ts:438-488](../../src/main/database/db.ts#L438-L488)（`searchMusicPinyin`/`searchMusicLike`）、[db.ts:2503-2559](../../src/main/database/db.ts#L2503-L2559)（`getSearchSuggestions`）
- **问题**：`search_pinyin`/`search_initials`/`title`/`artist` 等字段建了 B-tree 索引，但查询统一用 `LIKE '%q%'`，索引用不上，只能全表扫描。
- **影响**：大曲库下搜索框每次输入都可能触发多次全表扫描。

### H3. 曲库扫描逐文件写库，无事务批量提交
- **状态**：已修复
- **修复说明**：`MusicDatabase` 新增 `runInTransaction()`；`FileScanner` 改为把每个文件的判重后续写入（插入/更新/`local_music` 维护）收进实例级队列 `pendingWrites`，在每 100 个文件的 WAL checkpoint 节点、以及扫描的成功/取消/异常三个出口统一 `flushPendingWrites()`，用一个事务批量提交。并发调度（`executeWithConcurrency`）未改动；`onProgress` 仍在写入入队时触发，不等真正落盘。
- **位置**：[db.ts:518-758](../../src/main/database/db.ts#L518-L758)（`insertAllMusic`/`updateAllMusic`）、[fileScanner.ts:296-536](../../src/main/services/fileScanner.ts#L296-L536)
- **问题**：扫描时对每个文件单独调用 CRUD 方法，没有事务批量包裹；对比同文件里 `batchGetOrCreateMusicDir` 等已正确使用 `db.transaction()`，说明是遗漏而非设计选择。
- **影响**：首次扫描/大库导入耗时明显增加，可能造成主进程长时间占用。

### H4. Windows UNC/网络路径被 `normalizePath` 破坏
- **状态**：已修复
- **修复说明**：`normalizePath` 在坍缩连续分隔符前先判断并保留开头的 UNC 双斜杠前缀，再对剩余部分做原有的分隔符坍缩。已补充 `pathUtils.test.ts` 单测覆盖 UNC 路径规范化与文件名拼接，`npm run test` 全部通过。
- **位置**：[pathUtils.ts:28-50](../../src/main/database/pathUtils.ts#L28-L50)
- **问题**：`\\NAS\Music\...` 经过分隔符替换 + 合并连续分隔符两步处理后，开头的双斜杠被压缩成单斜杠，UNC 路径格式被破坏。
- **影响**：音乐库放在未映射盘符的网络共享目录时，扫描/回放会找不到文件（功能性阻断，非边缘 case）。

### H5. 单目录扫描的暂停/取消完全失效
- **状态**：已修复
- **修复说明**：`scanManager` 新增 `setScanner()`；`handlers.ts` 的 `scan-music-folder` 在创建 `FileScanner` 实例后立即注册给 `scanManager`，扫描结束（成功/异常）时同步清空，使通用的暂停/取消 IPC 能转发到真正在跑的扫描器。
- **位置**：[handlers.ts:401-461](../../src/main/ipc/handlers.ts#L401-L461)（`scan-music-folder`）、[scanManager.ts:25-141](../../src/main/services/scanManager.ts#L25-L141)
- **问题**：`scan-music-folder` 创建的 `FileScanner` 实例只更新了 `scanManager` 的状态标志，没有把实例本身交给 `scanManager.currentScanner`，导致通用的暂停/取消 IPC 找不到真正在跑的扫描器。
- **影响**：用户点"暂停/取消"，UI 显示已生效但扫描仍在后台跑；若随后再发起新扫描，可能出现两个扫描器同时写库的数据竞争。

### H6. 批量元数据/ID3 修复同步阻塞主进程
- **状态**：已修复
- **修复说明**：`metadataEditor.batchUpdateMetadata`、`id3Fixer.fixID3TagsBatch`、`metadataSync.batchSyncMusicMetadataToDb` 的批量循环里每处理完一个文件后插入 `await new Promise(resolve => setImmediate(resolve))`，让出事件循环，避免连续同步 IO 长时间占用主进程。函数签名未变。
- **位置**：[metadataEditor.ts:95-123](../../src/main/services/metadataEditor.ts#L95-L123)、[id3Fixer.ts:259-381](../../src/main/services/id3Fixer.ts#L259-L381)、[metadataSync.ts:280-326](../../src/main/services/metadataSync.ts#L280-L326)
- **问题**：循环体虽然写了 `async`/`await`，但内部实际是同步文件 IO（`nodeID3.read/write`、`copyFileSync`、`readFileSync`），没有任何让出事件循环的操作。
- **影响**：批量修复/同步上百首歌时，Electron 主进程事件循环被连续占用，期间所有 IPC（播放控制、托盘、扫描进度）都会卡住，应用整体无响应。

### H7. `LocalMusicList.vue` 重复注册扫描状态监听器，逻辑互相矛盾
- **状态**：已修复
- **修复说明**：把两个 `onMounted`/`onUnmounted` 合并为一组，只保留基于 `state.isScanning`/`state.isPaused` 的正确解析逻辑，删除错误的 `state?.status` 解析；`onScanProgress`/`onScanStateChanged` 各只注册一次；`music-updated`/`music-list-refresh` 订阅迁入合并后的 `onMounted`；`onScanStateChanged` 回调参数类型恢复为 `{ isScanning: boolean; isPaused: boolean }`。
- **位置**：[LocalMusicList.vue:393-492](../../src/renderer/components/music/LocalMusicList.vue#L393-L492)
- **问题**：组件里有两个独立的 `onMounted` 都调用了 `onScanProgress`/`onScanStateChanged`（`ipcRenderer.on` 会追加而非替换监听器）。两套回调对 `state` 的解析假设不一致：一套认字段 `isScanning`（正确），另一套错误地认字段 `status`（该字段实际不存在，永远为 `undefined`），两者依次同步触发，后一个错误回调会把 `isScanning` 强制覆盖为 `false`。
- **影响**：扫描进度条 UI 表现不可靠，进度条可能不显示或忽隐忽现。卸载时监听器有正确移除，不构成内存泄漏，但挂载期间状态错误是实打实的正确性 bug。

## 低严重度 / 观察项

### L1. `local-file://` 协议处理器无缓存，每次请求同步查库+`statSync`

### L2. 非分页列表接口与分页版本双轨存在
- **状态**：不予处理
- **原因**：`get-favorites-paginated`/`get-playlist-songs-paginated` 分页版本已存在，非分页版本仍被部分渲染层调用方依赖一次性全量数据；把这些调用方切到分页版本是跨渲染层的改动，超出本条"低严重度性能记录"的范围，不在本次处理。

### L3. Prepared Statement 未做实例级缓存
- **状态**：已修复
- **修复说明**：`MusicDatabase` 新增按 SQL 文本为 key 的公开方法 `prepareCached(sql)`（内部维护一个 `Map` 缓存），应用在两个确认的真实热点：`getSearchSuggestions`（拼法固定为 2 种变体，缓存命中率高）；`FileScanner` 扫描期间对每个文件的存在性检查（原来逐文件调用两次 `db.getDatabase().prepare(...)`，改为 `db.prepareCached(...)`）。未对 db.ts 全文所有 `.prepare()` 调用做扫荡式替换，其余路径调用频率低，改了收益不成比例。
- **位置**：`src/main/database/db.ts` 全文
- **影响**：热点路径（搜索建议、扫描期间存在性检查）有可避免的重复 SQL 编译开销，绝对耗时不大。
